# EPUB validator v5 | Hosted Colab implementation and acceptance reference

**For Astra 6.2 and Sol 6.2 · Research date 19 November 2026 · Drive REST v3 · Google Antigravity CLI 1.5.12 release baseline**

**Decision.** Build the interactive controller, ID-based Drive selection, read-only progress view, bounded staging and reviewer adapters. Two release gates remain open. First, the public Drive API evidence below does not establish that the service will reject an old notebook's queued write after another notebook takes ownership, or reject a move if the scanned bytes change just before commit. Second, the hosted runtime must demonstrate containment and observation for each actual reader. Until those gates pass, show the proposed disposition separately from its execution. A book can have a quarantine decision while its Drive move is pending.

**Evidence key.** *Documented* means the linked publisher describes the behavior. *Observed* means directly checked during this assignment. *Design* is an implementation recommendation. *Open* means the requirement still needs evidence. All external references below were consulted against the November 19 baseline. The eight hosted trials at the end are acceptance procedures.

**Observed environment.** Windows NT 10.0.26200.0. The project directory supplied briefs and research memos, including the v1–v4 contracts. It contained no executable validator, notebook, engine adapter, or monitor. A separate repository content request returned 404, which does not distinguish inaccessible from absent. The public Colab home page showed **Sign in** and linked Google's Antigravity-in-Colab example. No hosted runtime, account class, disposable Drive folder or reviewer credential was available for live trials. Local command discovery did not find `agy`. No hosted engine, authenticated CLI invocation, Drive mutation, takeover, or end-to-end regression passed during this research.

## 3. Drive selection, writes and recovery

**Discover by ID.** Configure IDs for intake and every destination. Reject overlapping roots or explicitly exclude every output subtree before descent. Treat the displayed path and filename as labels. For individual selections and recursive discoveries, fetch current metadata, walk parent IDs to intake, reject trashed/unresolvable ancestors and disallow selected outputs. For shortcuts verify both shortcut placement and target ancestry/identity, handle resource keys, detect cycles and recheck the target before use. A shared folder in My Drive differs from a shared drive. For a shared drive use the applicable `supportsAllDrives`, `includeItemsFromAllDrives`, `corpora=drive` and `driveId`; follow all page tokens and treat incomplete search as incomplete coverage. Revalidate on Resume. [Files list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list) · [Shortcuts](https://developers.google.com/workspace/drive/api/guides/shortcuts) · [Shared drives](https://developers.google.com/workspace/drive/api/guides/enable-shareddrives)

**Identify the bytes.** Record Drive ID, drive and parent IDs, MIME type, size, version, available binary head revision and hashes. Stream bytes through SHA-256. Drive's monotonically increasing `version` includes metadata changes. A matching name, timestamp, MD5 alone, or stale revision is insufficient. If SHA-256 is missing, re-download and hash, bracketing the read with metadata checks. Recheck source, current accepted head, exact candidate hash, destination and settings before authorization. A changed version with identical bytes still requires membership, permissions and policy revalidation. Revision retention is limited. Blob revisions can be pinned with `keepForever`, up to 200 per file. Preserve accepted editions as separately identified files. [File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) · [Revisions](https://developers.google.com/workspace/drive/api/guides/manage-revisions)

**Write protocol.** Persist one intent per operation before dispatch, including operation ID, book ID, hashes, source and destination IDs, accepted head, configuration digest, approval IDs, writer generation and intended output ID. A quarantine move uses `files.update` with `addParents` and `removeParents` on the original file. Test source move and destination add capabilities, shared-drive restrictions, ownership and post-move access. A copy followed by deletion has different failure and preservation semantics. For new binary outputs allocate and persist a `files.generateIds` ID before `files.create`. Retrying a successful create with that same ID yields a conflict, which can be reconciled by reading the object. Names can collide. Never replace the first same-name match. [Move files](https://developers.google.com/workspace/drive/api/guides/folder) · [Generate IDs](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds) · [Create files](https://developers.google.com/workspace/drive/api/guides/create-file)

**Concurrency verdict.** A fixed, agreed-in-advance file ID can help two sessions contend for *initial creation* of one lock record. Independent generated IDs or a list-by-name lock cannot. The v3 update method documents no condition tying a target PATCH to the current generation of a separate writer record or to the current SHA-256 of another file. A batch groups independent calls and permits reordering. Even a demonstrated conditional update of the lock alone would leave the target operation unguarded. Counterexample: A verifies generation 7 and queues a move. B takes generation 8. The service then receives A's already authorized move on the book ID. Both notebooks can have followed the proposed preflight rules. A final read can detect damage only after it occurs. The same gap affects a newly edited source and an occupied destination checked by name. [Update method and parameters](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update) · [Batch semantics](https://developers.google.com/workspace/drive/api/guides/performance)

**Release consequence.** Require an enforceable server-side condition at each consequential write, including queued requests, resumable completion and approval-state transitions, or another demonstrably equivalent construction within scope. An expiry, heartbeat, disabled button, lock-file version, explicit takeover dialog or a claim that the old runtime disconnected cannot supply it. Keep ordinary inspection and readback available. Until qualified, leave automatic moves, publication and ownership-dependent mutations pending, including expiry deletions. Do not advertise an automatically writable intake solely because one session is visible. A blocker shared by the intake pauses affected writes across it. A changed book or inaccessible output pauses only its dependent work.

### Recovery table

On reopen, inspect journal and Drive without mutation. After an explicit Resume recheck writer authority, selected account, policy/configuration identity and all referenced objects. “Complete” below means automatic recognition from evidence. Every instruction to issue a new write is conditional on the concurrency gate above.

| Interruption or conflict | Evidence to read from Drive | Reconciliation and scope |
|---|---|---|
| Before quarantine move | Original ID and expected hash still in exact intake parent, destination permissible, recorded intent valid. | Still pending. Reissue only with an enforceable source and writer guard. If disposition is report-only, record the preview without a move. |
| After move, before acknowledgement | Same untrashed file ID, expected bytes and exact quarantine parent, with matching intent. | Recognize desired state without moving again. Record observed completion without inventing proof of who moved it. Other parent, changed bytes or unexpected copy → ambiguous book. |
| Before output upload | Persisted generated ID, expected hash/size, intended parent, approvals and candidate still valid. Absence established with suitable visibility. | Resume same intent and ID. If staging disappeared, reconstruct candidate, hash and requalify as required. A concealed object can return 404. Absence by name is insufficient. |
| Interrupted resumable transfer | Store the session URI only in protected session state. Query upload status with empty PUT and `Content-Range: bytes */TOTAL`. A 308 response identifies received range, possibly empty. | Continue from server-confirmed offset with identical bytes. A final success indicates completion, subject to object verification. Session URLs expire (normally one week). If unavailable, reconcile the reserved ID before starting a new transfer with that ID. Never log the URI or resume blindly. [Upload protocol](https://developers.google.com/workspace/drive/api/guides/manage-uploads) |
| After upload, before receipt or journal acknowledgement | Reserved ID exists. Check parent, content hash/size, operation binding and verified candidate. | Matching evidence → complete once. A 409 on retry triggers the same readback. Wrong parent, occupied destination under policy, hash discrepancy or hidden object → pause that book, preserve earlier editions. |
| Source, proposal or configuration changed | Compare current bytes and ancestry, reviewed head, exact diff, candidate hash, settings and approval records. | Preserve source and earlier versions. Offer fresh scan/proposal for changed bytes. Rerun affected gates for changed settings. Unaffected books continue. A matching passage cannot rescue a stale book-wide edit approval. |
| Permission lost, quota or transient error | Inspect HTTP status and reason. 403 can indicate rate limit or denial. 404 can conceal inaccessible files. Verify account, folder capabilities and remaining visibility. | Back off with jitter and a bounded retry budget for rate limits/429 or recoverable 5xx. Refresh authentication where appropriate. Reconcile uncertain writes first. Pause dependent books or the shared service if quota is exhausted. [Errors](https://developers.google.com/workspace/drive/api/guides/handle-errors) · [Quota limits](https://developers.google.com/workspace/drive/api/guides/limits) |
| Competing sessions or uncertain takeover | Look up the pre-agreed writer identity and generation. Determine whether the commit service rejects delayed old-generation requests. | Second session inspects status. Require explicit takeover. Without enforceable rejection leave affected durable writes pending across the intake. Retry the same operation only after qualification. |
| Trace expiry while offline | On next authorized run enumerate only journaled trace IDs in dedicated evidence folder. Verify identity, expiry, folder and decision-retention policy. | Keep durable decisions, digests and attribution summaries. Restrict detailed traces for held/quarantined books. Trash is recoverable until purged, ordinarily after 30 days. Permanent delete has distinct permissions and consequences. Record the action actually taken. Never empty the account's trash to meet scoped expiry. [Trash and deletion](https://developers.google.com/workspace/drive/api/guides/delete) |
## 4. Implementing the third reviewer

**Distribution.** Google's native Linux installer is published at `https://antigravity.google/cli/install.sh` and normally installs `~/.local/bin/agy`. The official releases page has a CLI selector. On hosted Colab first inspect the existing binary. Record the resolved path, architecture, `agy --version`, digest and supported flags. Use an approved, version-specific Linux artifact or a previously verified build manifest. The moving installer and a self-reported version alone cannot establish reproducibility. I could verify the documented installer entry point and 1.5.12 changelog, but could not independently retrieve the installer bytes or establish a vendor signing key, published checksum for the selected binary, fixed-version installer switch, or minimum libc for the standalone CLI. Keep a pin unavailable until the released artifact and expected digest are independently qualified. Do not apply desktop IDE system requirements or updater settings to the CLI without checking. Verify the digest again after launch/update opportunities. [Install](https://antigravity.google/docs/getting-started?tab=cli) · [Release selector](https://antigravity.google/releases) · [CLI changelog](https://antigravity.google/docs/changelog?tab=cli)

**Headless contract.** In the restricted reviewer process, first inspect `agy --help`, `agy --version` and `agy models`. Select an entitled model explicitly. For the hosted smoke test, use an operator-authored schema with one required string field and validate that it equals the supplied random test marker. The following is a documented command shape, not a recorded invocation:

```sh
agy -p "Return this public test value in the marker field: $PUBLIC_TEST_MARKER" \
  --model "$APPROVED_MODEL" --mode plan --disable-slash-commands \
  --output-format json --json-schema /policy/probe.json --print-timeout 90s
```

Supply the marker as trusted test input together with the prompt. In production pass an argv list and bounded stdin directly. The CLI documents text or structured `stream-json` input and text, single JSON or newline-delimited `stream-json` output. For one-shot requests parse the final envelope's `structured_output`, `status`, `conversation_id` and `usage`. For streams check the final result, including schema, and reject a truncated stream. Require successful exit, `SUCCESS`, a valid schema, correct job binding and size limits. `ERROR`, `CANCELED`, `INTERRUPTED`, `INVALID`, `WAITING` and a residual `RUNNING` cannot complete a finding. Separate stderr from stdout and redact both before persistence. Set the CLI timeout explicitly (default 0s disables it) plus a parent wall-clock deadline and child-tree cleanup. Interactive `/usage` or `/quota` can help an operator; token counts are consumption, not an entitlement or guarantee of remaining requests. Treat sign-in prompts, provider limits, network timeouts and malformed output as resumable interruptions. [Headless protocol](https://antigravity.google/docs/cli/headless/) · [CLI reference](https://antigravity.google/docs/cli/reference/)

**Access and independence.** Give each invocation an empty private working directory with no repository ancestor, a controlled HOME/config, and read/search access to the *one* verified extracted book. Use synthetic member names or a read-only content broker. The trusted dispatcher owns the credential, finding identifier, input limits and diagnostic interface. Permit only named, argument-validated operations such as counting variants or comparing headings. Precomputed diagnostics suffice for fixed queries. For interactive book search, expose a constrained read/search interface. Hide shell, notebook editing, file writes, browser, arbitrary HTTP, package managers, remote control, inherited MCP servers, skills, hooks and parent sessions. Scrub project/global settings, including instructions derived from archive members. Verify effective tools at launch and exercise denials. Plan mode, deny/ask/allow rules and `--sandbox` are useful layers, but an unavailable OS sandbox or powerful pre-approved tool defeats the boundary. If a safe tool inventory or separate credential/process boundary cannot be demonstrated, only that reviewer is pending. [Permissions](https://antigravity.google/docs/permissions/) · [CLI settings](https://antigravity.google/docs/cli-settings) · [Hosted notebook powers](https://colab.research.google.com/notebooks/antigravity_cli.ipynb)

Use the same content contract for `codex exec --ephemeral --sandbox read-only --json --output-schema SCHEMA` and `claude -p --output-format json --json-schema SCHEMA_JSON --no-session-persistence`. Inspect actual installed help. Codex event JSON and Claude's result envelope require separate adapters. For Claude restrict tools and explicitly exclude unapproved MCP servers. For Codex read-only filesystem mode alone still permits shell reads, so qualify the outside boundary and effective tool configuration. Avoid continuation flags and session reuse on all three. A fresh process can still inherit account-synced settings, system instructions or a workspace plugin. [Codex execution](https://developers.openai.com/codex/noninteractive/) · [Claude CLI](https://code.claude.com/docs/en/cli-reference)

Google's older `gemini -p`, npm package `@google/gemini-cli`, Gemini CLI approval flags and its JSON event schema belong to a different program. Its login variables and model routes do not establish `agy` behavior. Google added model support specific to the API-key route in 1.5.12. Pin the client, requested model, mode and authentication route in evidence. [Google migration notice](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/) · [Antigravity release history](https://antigravity.google/docs/changelog?tab=cli)

**V3 and Resume.** Display a configured pair of distinct CLIs and allow the operator to change it before requesting a second opinion. Start no provider calls during setup beyond a separately requested authenticated smoke test, or during scanning or repair. For review select the latest accepted edition, otherwise verified intake. Show the operator which book content the selected provider may receive. Give the second reviewer the same finding, bytes and diagnostics in a new context, withholding the first response, proposed diff and notes. Capture supporting locations, rationale, diagnostics, CLI/model identity and exact diff. Present both opinions side by side. Neither reviewer can approve, modify or publish.

Use one stable proposal ID in widgets and exported records. Bind approval to the complete book hash and exact displayed diff. On Resume verify both plus configuration, eligibility, candidate hash, behavioral result and publication decisions. Preserve occurrence-level intentional findings across unrelated edits, reopen changed occurrences, and never transfer an edit approval to a changed book. If the approved edit leaves its target warning, obtain a separate publication decision on the exact verified candidate. Preserve earlier editions. On quota or sign-in loss keep committed findings, pause unfinished ones with the same reviewer, and require an explicit request before sending content to a different provider. A provider may have processed a request whose response was lost. Record this uncertainty and do not equate a retry with exactly-once billing.
