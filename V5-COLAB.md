# EPUB validator v5 in Google Colab

Open [EPUB-validator-v5.ipynb](EPUB-validator-v5.ipynb) in hosted Colab, connect a CPU runtime, and run the notebook cell. The notebook embeds a digest-checked copy of the validator and is distributed with empty outputs. Regenerate it from this checkout with `python tools/build_colab.py`.

1. Select **Set up**. Automatic installation targets Ubuntu 24.04 on amd64 with system Python 3.12. It installs from a dated, Ubuntu-signed APT snapshot and verifies installed package versions, pins every EPUBCheck 5.4.0 JAR, installs WeasyPrint 70 and its hash-locked Python dependencies, then invokes FreshClam. The setup report identifies installed tools and separately reports static scanning, Qt and WeasyPrint, the monitor, and their controls. A failed prerequisite leaves dependent work pending.
2. Select **Connect Drive** and authorize the Drive API. Enter IDs for six dedicated folders. Select folders or EPUBs by ID. Blank selection means the intake itself. The notebook resolves shortcuts and checks ancestry against the intake and all output subtrees. Shared locations need sufficient permissions to establish ancestry, read EPUB content and perform the requested Drive operation.
3. **Run** a preview with **Report-only** enabled. Reports display the decision and proposed operation. With the behavioral gate enabled, both distinct engines and their monitors must qualify before a batch starts. You can explicitly run static inspection alone. It can establish quarantine, while static-clear books remain pending behavioral inspection. Repair requires behavioral inspection. The notebook stages one book at a time and reserves space for all concurrent input, candidate, and sandbox scratch bytes. Installed tools, signatures, and the durable journal are outside the book-staging allowance. A runtime holds an exclusive staging lease. Setup reaps only previously owned staging roots whose lease is unlocked.
4. **Open status** reads the canonical journal before running anything. Authorize **Resume** to continue the same configuration. Use **Fresh scan** to refresh selected books after input or configuration changes. **Take over and resume** explicitly transfers writer ownership after reconciling a pending physical operation. A guarded failure can leave one book pending or ambiguous while unrelated decisions continue. **Download report** exports a local JSON report.

## Journal provisioning and conditional operations

Use dedicated test folders for first qualification. With a trusted Drive API client and the same signed-in account, provision each intake once as follows.

- **Journal template** displays a correctly bound empty document. Upload that document as a binary `application/json` file directly in the configured reports folder. Set the intake folder's public Drive custom property `epubValidatorV5Journal` to that object's ID using `files.update`. Keep the mapping and reports folder stable while using the intake. Enter the journal ID in the notebook. A different object ID or account cannot acquire this writer lane. A collaborator may see the underlying Drive objects according to their Drive permissions.
- To qualify journaling, upload a **separate disposable** binary application/json file to the same reports folder containing `{"purpose":"epub-v5-disposable-cas-probe"}`. Enter its ID and turn off **Report-only**. Select **Qualify disposable writes**. The test must read a strong media ETag, conditionally update the probe, observe a new ETag, and observe rejection of a deliberate stale conditional write. If qualification fails, preview and read-only status remain available. A probe that accepted a stale write is marked refused. Review the failure before provisioning a replacement.
- To store detailed held or quarantined traces, upload the generated evidence template as a binary application/json file directly in the evidence folder. Set that folder’s public custom property `epubValidatorV5Evidence` to the file ID. The notebook updates the evidence file through a conditional intent, gives each trace its own slot, and expires details from the current version while preserving the decision record and digest. Drive revision history has separate retention. For the optional quarantine lane, create two disposable subfolders directly below reports. Set the public custom property `epubValidatorV5Probe` to `disposable` on each and on a harmless test binary placed in one. Enter those three IDs and run the disposable qualification. It replaces the disposable binary with harmless probe bytes, checks that both content and metadata changes reject stale moves, then reads back a current conditional move. Repeat using the same storage class as the quarantine flow.
- Automatic quarantine is enabled only for direct children of intake, to the same Drive storage class as the qualifying probe, and after verifying available capabilities, the scanned source identity and bytes, and an unoccupied destination name. It registers one physical intent by journal CAS before dispatch. Resume recognizes the move by ID, parent, revision and digest or retries an unchanged exact intent. Explicit takeover fences a delayed physical request against its original source ETag before switching the journal generation. If the relevant permissions, ETag or source identity cannot be established, the affected action remains pending or ambiguous. An out-of-band folder relocation or provisioning change is unsupported while an intent is active. If an intent cannot be reconciled, new physical operations stay behind the writer barrier. Its current owner can still record independent decisions. A session unable to take over can inspect status and preview independent pending books in read-only mode.
- Repair intake copies and edition publication remain pending. Journal CAS and single-object quarantine CAS cannot make a new edition atomically contingent on both another Drive object's live revision and the current generation. A name check alone also cannot reserve a Drive folder name. The repair worker can build and re-inspect exact candidate bytes and records the verified digest. Previously published editions are preserved. The separately qualified binary staging lane can save candidates up to 5 MiB to a reserved, unpublished evidence object. It never relocates that object into repaired editions. If no evidence file is configured, trace details stay in the runtime and their Drive transfer remains pending. The journal records the durable decision, trace digest and expiry.

To qualify unpublished candidate staging, use **Staging template** to obtain the `disposable` template and provision it as a binary `application/octet-stream` file in evidence. Set its public custom property `epubValidatorV5Candidate` to `disposable`. Enter its ID in **Binary CAS probe ID** and repeat **Qualify disposable writes**. The binary probe checks that a metadata change fences the old media token and that a fresh PATCH reads back exact bytes. For each actual staging slot, provision a separate object in that same Drive and evidence folder using its selected book ID as the template and property value. Select **Stage verified candidate** with that slot ID after repair verifies a candidate. The notebook rebuilds and re-verifies the exact digest, journals the intent, and checks the uploaded bytes by object ID. If disconnected, requalify the routes and explicitly resume. The notebook recognizes a completed update or fences and retries against the reserved slot when the source and exact candidate still qualify.

Drive authentication, explicitly requested provider requests, trusted setup downloads and signature updates run in the controller. Parsing and rendering run under an unprivileged supervisor inside an outer Bubblewrap sandbox. The nested static and renderer workers retain their original namespaces and read-only mounts. The outer namespace also contains the renderer monitor. Qt uses Qt 5 QTextDocument. The other engine is WeasyPrint. Qualification uses a clean itinerary, separate benign images with local and loopback targets, a live loopback positive control, and disposable outside-file, notebook, Drive and credential markers. The reader controls include kernel socket and process-dispatch denials. A kernel that denies nested user or networking namespaces, monitor startup, or working containment leaves dependent work pending.

## Review

Select a primary and distinct second reviewer. Select an eligible book ID, choose a finding, and explicitly request a review. The dispatcher gives the provider the selected finding and only the slices requested through the existing bounded read, search and diagnostic protocol. Second opinion starts with fresh context and no first response. Export and the notebook use the same proposal ID and exact diff. Approval and a separate persistent-warning publication decision recheck the selected source and candidate bytes, and record the result in the conditional journal.

- **Codex CLI** supports configuring an approved native Linux ELF executable, exact SHA-256 pin, explicit model, and the `OPENAI_API_KEY` Colab Secret. **Claude Code CLI** uses the same flow with `ANTHROPIC_API_KEY`. Configure and test only the desired reviewer. The smoke request uses a disposable public marker. The actual provider key stays in the trusted, text-only relay. The native CLI runs with a ticket in a private network namespace and receives no Drive credentials, shared folder mount, or general internet access.
- ChatGPT per-session/device sign-in and Claude Code login/OAuth token are listed as pending. Their authentication paths are not qualified in the isolated relay. **Antigravity CLI** accepts a pinned Linux ELF binary and explicit Gemini model for a disposable local routing probe. The endpoint overrides are compatibility candidates. The relay rejects unknown routes, native-tool declarations and configuration, and non-text content. A routing marker establishes relay compatibility only. Plan mode and disabled slash commands do not establish denial of in-process native tools. With that prerequisite unavailable, reviewer calls remain pending and the notebook never requests its `GEMINI_API_KEY` secret. Genuine CLI compatibility, authenticated service access, Google sign-in and dedicated ADC remain pending.
- Reviewer binary installation and pin trust are operator-supplied. The headless clients must support the v3 restrictive flags. A changed binary, invalid or missing credentials, model limits, or failed sandbox leaves that review pending without affecting unrelated discovery and inspection. Provider requests interrupted after dispatch may have incurred usage.

Hosted Colab and real Drive qualification require the participating account and runtime. Local tests and disposable Linux guest qualification do not establish the hosted results. See the separate acceptance report for observed scenarios.
